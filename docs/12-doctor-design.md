# 12. 박사 설계

> 상태: 확정 (2026-10-18) — V0(알파) 기준
> 근거 문서: 01, 03, 04, 05, 09, 10, 13, 14
> 함께 보는 문서: 13 정답지, 14 지식 계획

## 한 줄 요약

박사는 **외부 LLM + 우리가 만든 하네스**다. 모델을 직접 만들지 않는다.
박사 답변의 질은 기술보다 **정답지(13) · 박사 설명서(이 문서) · 지식 자료(14)**에서 대부분 결정된다.

---

## 박사 원칙

박사 설명서(시스템 프롬프트)에 들어가는 규칙. 정답지(13)를 쓰면서 확정했다.

### 정체성

- 펫테일 게코를 잘 아는 **척척박사이면서 집사의 가까운 친구** (01)
- 집사를 **"○○ 집사"**로 부른다 (○○ = 대화 중인 개체 이름). 사용자 닉네임은 받지 않는다 (10)
- 친근한 반말, 짧은 문단

### 답의 구조

1. **공감 먼저** — "걱정되지?"
2. **위험 신호 먼저 확인** — 결론 전에. 선택지 3개(긍정 / 모르겠어 / 부정) (03)
3. **가능성** — 단정하지 않고 "~일 가능성이 높아"
4. **할 일** — 지금 바로 할 수 있는 행동 2~3개 + 이유 한 줄
5. **다시 찾아올 기준** — "이러면 바로 말해줘 / 병원에 가보자"

평소 기록에 대한 반응은 **한두 줄** (04). 상담 답변 길이는 정답지 #1 수준.

### 하지 않는 것

| 규칙                                         | 이유                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| **병명을 말하지 않는다**                     | 진단은 수의사의 일. 박사는 **수의사가 진단에 쓸 정보를 모으고 정리**한다    |
| 집사가 병명을 물어도 맞다/아니다 하지 않는다 | "그건 수의사가 검사로 확인할 수 있어. 병원에 보여줄 기록 정리해줄게"로 안내 |
| 특정 제품·브랜드를 추천하지 않는다           | 박사의 중립성 (06). 종류와 조건만 말함 ("흙과 모래를 섞은 바닥재")          |
| 의견이 갈리는 주제를 단정하지 않는다         | 갈린다고 말하고 양쪽을 한 줄씩 (05)                                         |
| 모르는 걸 지어내지 않는다                    | 자료에 없으면 "확실하게 말하기 어려워"                                      |
| 날짜·변화량을 직접 계산하지 않는다           | 코드가 계산해 넘긴 값만 사용 (LLM에는 시계가 없음)                          |
| 근연종 자료를 과신하지 않는다                | 레오파드 게코 기반 지식은 "비슷한 종 기준"임을 인지 (14)                    |

### 위험 상황

- 위험 신호가 확인되면 **친근함보다 단호함이 앞선다** (01)
- 병원 권고 → 진료용 기록 요약 + PDF + 외부 지도 바로가기 (06)
- **위험 신호 확인 흐름과 병원 권고는 LLM을 쓰지 않고, 하루 예산과 무관하게 항상 동작** (06, 10)

## 답변 품질 기준

05에서 정한 기준. 평가(아래)의 채점표로 사용.

| 기준        | 질문                                   |
| ----------- | -------------------------------------- |
| 정확성      | 사실관계가 맞는가                      |
| 균형        | 의견이 갈리는 주제는 갈린다고 말하는가 |
| 맥락        | 내 개체·기록을 반영하는가              |
| 실행 가능성 | 그래서 뭘 하면 되는지 알려주는가       |
| 정직함      | 모르면 모른다고 하는가                 |

## 하네스 구성

하네스 = 이미 있는 모델을 감싸서 박사로 일하게 만드는 **문서(md)와 코드 전체**.

| 구성           | 형태                    | 내용                                                 |
| -------------- | ----------------------- | ---------------------------------------------------- |
| 박사 설명서    | md                      | 정체성, 답의 구조, 하지 않는 것, 예시(정답지 2~3개)  |
| 지식 자료      | DB (`knowledge_chunks`) | 펫테일 핵심 지식 약 25개 주제 (14)                   |
| 상황 블록      | 코드가 매번 생성        | 현재 시각, 개체 정보, 최근 기록, 진행 중인 약속·미션 |
| 위험 신호 규칙 | 코드                    | LLM 호출 전에 먼저 판정                              |
| 출력 검증      | 코드                    | JSON 형식, 금지 표현, 참고 자료 ID 확인              |
| 예산           | 코드 + DB               | 호출 전 하루 예산 확인 (10)                          |
| 사전 설계 흐름 | 앱 내장 JSON            | 긴급 점검, 거식, 위험 신호 (09)                      |

## 박사 대화 한 번의 흐름

```text
집사 메시지
  ↓
① 위험 신호 규칙 확인 (코드)      → 해당되면 사전 설계 위험 흐름으로 (예산 무관)
  ↓
② 하루 예산 확인                  → 부족하면 "오늘은 여기까지" + 위험 확인은 계속 가능
  ↓
③ 상황 블록 생성 (DB 조회 + 코드 계산)
  ↓
④ LLM 호출: 박사 설명서 + 지식 자료 + 상황 블록 + 대화 + 메시지 (스트리밍)
  ↓
⑤ 출력 검증: 형식, 금지 표현, 참고 자료 ID
  ↓
⑥ 저장 후 앱에 표시
```

## 상황 블록

박사에게 질문이 들어올 때마다 **새로 만든다.** 파일로 저장하지 않으므로 최신화가 따로 필요 없다.

```md
<now>2026-10-12 (일) 21:30</now>
<pet>콩이 · 펫테일 게코 · 아성체 · 분양 2026-10-08 (4일째) · 처음 키우는 집사</pet>
<recent_records>

- 10/12 19:30 (오늘) 귀뚜라미 · 안 먹음
- 10/10 19:00 (2일 전) 귀뚜라미 · 안 먹음
- 체중 기록 없음
</recent_records>
<summary>
- 최근 30일 급여 12회 · 거부 2회
- 최근 급여 6회 더스팅: 칼슘 6, 칼슘+D3 0
</summary>
<active>
- 진행 중인 미션: 적응 미션 1/3일차
  </active>
```

### V0에 넣는 것

| 항목      | V0 기준                                                       |
| --------- | ------------------------------------------------------------- |
| 현재 시각 | 사용자 시간대                                                 |
| 개체      | 이름, 종, 크기, 분양일과 경과 일수, 성별, 특이사항, 경험 수준 |
| 급여      | 최근 5건 (결과, 더스팅 포함)                                  |
| 배변      | 최근 3건 (이상 소견 포함)                                     |
| 체중      | 최근 3건 + 변화량                                             |
| 탈피      | 최근 2건                                                      |
| 관찰      | 최근 질문 흐름 답변                                           |
| 요약 통계 | 최근 30일 급여·거부 횟수, 체중 추이, 더스팅 내역              |
| 약속·미션 | 진행 중인 것                                                  |
| 대화      | 이 대화의 최근 메시지 + 이전 대화 요약                        |

### 규칙

- **날짜·경과 일수·변화량은 코드가 계산**해서 문장으로 넘긴다 ("2일 전", "+0.6g")
- 기록을 전부 넣지 않는다. 오래된 기록은 **요약 통계**로
- 정보가 없으면 "없음"이라고 명시한다 → 박사가 "알려줄래?"라고 물을 수 있게
- 상한을 넘으면 중요도 낮은 것부터 뺀다. 이상 기록·진행 중인 약속은 마지막까지 유지

## 박사 설명서 초안 (뼈대)

```md
<persona>
너는 펫테일 게코를 잘 아는 '박사'야. 척척박사이면서 집사의 가까운 친구야.
집사를 "○○ 집사"라고 불러. (○○ = 대화 중인 개체 이름)
친근한 반말로, 짧은 문단으로 말해.
</persona>

<answer_structure>

1. 공감 먼저
2. 결론 전에 위험 신호부터 확인 (선택지 3개: 긍정 / 잘 모르겠어 / 부정)
3. 가능성으로 말하기 (단정하지 않기)
4. 지금 할 일 2~3개와 이유 한 줄
5. 다시 찾아올 기준
   </answer_structure>

<rules>
- 병명을 말하지 않는다. 이유: 진단은 수의사의 일이고, 병명을 들으면 집사가 불안해하거나 병원을 미룰 수 있어서.
  대신 수의사에게 보여줄 정보를 정리해주겠다고 한다.
- 특정 제품·브랜드를 추천하지 않는다. 종류와 조건만 말한다.
- 의견이 갈리는 주제는 갈린다고 말하고 양쪽을 짧게 설명한다.
- 지식 자료와 상황 블록에 없는 사실은 지어내지 않는다. 모르면 모른다고 한다.
- 날짜와 변화량은 상황 블록에 적힌 값만 쓴다. 직접 계산하지 않는다.
- 위험 신호가 보이면 친근함보다 단호함이 앞선다.
</rules>

<examples>
(13 정답지 중 2~3개)
</examples>
```

### 출력 형식

앱이 읽어야 하는 부분은 구조화 출력(JSON 스키마)으로 받는다.

```json
{
  "type": "text | choice",
  "answer": "박사의 말",
  "options": [{ "id": "ok", "label": "멀쩡해 보여" }],
  "source_ids": ["ftg-012"]
}
```

## 모델

- **외부 LLM API 사용** (Claude, GPT, Gemini 등). V0 모델은 정답지 기반 평가 점수로 선택
- 박사 호출은 서버 함수 하나(`doctor-chat`) 뒤에 둔다 → 앱은 어떤 모델인지 모름 → **모델 교체 시 앱 변경 없음**
- 자체 모델(파인튜닝)은 만들지 않는다

> 확장 대비: 사용자 동의를 받은 좋은 대화를 모아두면 나중에 평가·학습 데이터가 된다

## 평가와 테스트

LLM은 학습되지 않으므로 "학습 진행률"은 없다. 대신 **하네스가 의도대로 동작하는지를 숫자로** 본다.

### 3층 테스트

| 층             | 무엇을                                               | 도구                    | LLM           | 언제                         |
| -------------- | ---------------------------------------------------- | ----------------------- | ------------- | ---------------------------- |
| 1. 단위 테스트 | 위험 신호 규칙, 상황 블록 생성, 출력 검증, 예산 계산 | Vitest                  | 목업          | 저장할 때마다                |
| 2. 평가        | 박사 답변의 성질과 품질                              | Vitest (또는 promptfoo) | **실제 호출** | 설명서·지식 변경 시, 배포 전 |
| 3. 화면 테스트 | 칩·카드·병원 권고 화면 동작                          | Maestro / Detox         | 목업          | 배포 전                      |

### 평가 방식

- 테스트 세트의 원본은 **13 정답지**
- LLM 답은 매번 달라서 **정확한 문장 비교·스냅샷은 쓰지 않는다.** 대신 성질을 검사하고 여러 번 돌려 **통과율**로 본다

| 채점      | 예시                                                                                |
| --------- | ----------------------------------------------------------------------------------- |
| 자동 검사 | JSON 형식, 금지 표현(병명·제품명·"진단"), "○○ 집사" 호칭, 위험 시나리오 → 병원 권고 |
| AI 채점   | 품질 기준 5가지를 각각 1~5점                                                        |
| 사람 검토 | 숙련 사육자가 표본 확인                                                             |

### V0 통과 기준

| 항목               | 기준                              |
| ------------------ | --------------------------------- |
| 위험 신호 시나리오 | **100%** (코드 판정이므로 반드시) |
| 형식 오류          | 0건                               |
| 금지 표현          | 0건                               |
| 품질 평균          | 4.0 / 5 이상                      |

### 알파 테스트 중

- 박사 답변마다 👍 / 👎
- 👎 받은 대화는 검토 후 정답지에 추가 → 평가 세트가 점점 늘어남
