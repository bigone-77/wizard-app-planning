# 05. 상세 시나리오 #3: 숙련자 B의 첫 평가

> 상태: 초안 확정 (2026-10-07)
> 페르소나: B 숙련자 친구 (평가자 역할)
> 범위: 평가자 역할만 다룸. 실사용자 역할(Wi-Fi 센서)은 V2 메모 참고

---

## 상황 설정

- 태일이 "요즘 이 앱 쓰는데 괜찮더라"며 B에게 추천
- B는 반신반의하며 설치. 키우는 개체 중 펫테일 한 마리로 테스트
- B의 속마음: "또 인터넷 정보 짜깁기한 앱 아니야?"

---

## 흐름

### ① 첫 인사 질문 — 앱 전체 온보딩의 시작점

```text
🧑‍🔬 "반가워! 나는 너랑 도마뱀을 도와줄 박사야.
     혹시 지금 어떤 상황이야?"

[아직 데려오기 전이야]        → 1A 준비형 태일
[막 데려왔어, 처음 키워봐]    → 1B 충동형 태일
[키워본 적 있어]              → B 숙련자
```

| 선택             | 다음 흐름                              | 개체 등록                               |
| ---------------- | -------------------------------------- | --------------------------------------- |
| 아직 데려오기 전 | 준비물 체크리스트, 분양 시 질문 리스트 | 입양 후에 등록                          |
| 막 데려옴, 처음  | 긴급 환경 점검 → 개체 등록 → 입문 코스 | 필수 항목만, 나머지는 박사가 점진적으로 |
| 키워본 적 있음   | 바로 개체 등록 → 관리 화면             | 필수 항목 + 선택 항목 펼침              |

- **화면과 데이터 구조는 하나.** 등록 화면은 동일, 선택 항목의 접힘/펼침만 다름
- 경험 수준은 DB에 하나의 값으로 저장 → 박사의 설명 깊이 조절에도 사용
  - 초보: "바닥 온도가 왜 중요하냐면…"까지 설명
  - 숙련자: 핵심만
- 경험은 종·시간에 따라 바뀌므로 **설정에서 변경 가능**

### ② B가 박사를 시험한다

쉬운 질문(온도 등) 대신 **사육자들 사이에서도 의견이 갈리는 질문**:

> "펫테일한테 UVB 조명 필요해?"

배경: 야행성이라 UVB 없이 칼슘·D3 보충제로 키우는 방식이 오래 쓰였고, 최근엔 약한 UVB가 도움이 될 수 있다는 권장도 늘어남. 정답이 하나인 질문이 아님.

### ③ 박사의 답변

❌ B를 실망시키는 답변 (단정)

> 🧑‍🔬 "펫테일 게코는 야행성이라 UVB가 필요 없어!"

✅ B를 납득시키는 답변

> 🧑‍🔬 "이건 사육자들 사이에서도 의견이 갈리는 부분이야. 야행성이라 UVB 없이 칼슘·D3 보충제로 키우는 방식이 오래 쓰였고, 최근엔 약한 UVB를 주면 도움이 될 수 있다는 의견도 많아져. 지금 D3 들어간 보충제를 쓰고 있다면 필수는 아니고, 넣는다면 은신처로 피할 수 있게 일부에만 약하게 주는 게 좋아."
>
> ▸ 참고 자료 보기

### ④ 근거 확인

B는 "참고 자료 보기"를 펼쳐 어떤 자료를 바탕으로 한 답인지 확인한다. 태일은 평소 접어둔 채로 대화만 본다.

### ⑤ 결말

B가 답변과 참고 자료를 보고 "생각보다 제대로네"라고 판단.
이후 다른 초보 친구가 질문하면 "일단 이 앱 깔아서 박사한테 물어봐"라고 추천.

→ **숙련자의 신뢰가 초보 유입 경로가 된다.**

---

## 박사 답변의 품질 기준

시스템 프롬프트 작성과 답변 품질 테스트에 체크리스트로 사용.

| 기준        | 질문                                   |
| ----------- | -------------------------------------- |
| 정확성      | 사실관계가 맞는가                      |
| 균형        | 의견이 갈리는 주제는 갈린다고 말하는가 |
| 맥락        | 내 개체·사육 환경을 반영하는가         |
| 실행 가능성 | 그래서 뭘 하면 되는지 알려주는가       |
| 정직함      | 모르면 모른다고 하는가                 |

## 참고 자료 보기: 기술 방식

### 원리: 지식 자료에 번호표를 붙인다

```text
knowledge_chunks
  id: "S12"
  content: "펫테일 게코는 야행성으로, 전통적으로 UVB 없이 칼슘·D3 보충제로 사육되어 왔다…"
  source_title: "○○ 파충류 사육 가이드"
  source_url: "https://..."
```

LLM에 자료를 ID와 함께 넘기고, 답변과 참고한 ID를 구조화된 형태로 받는다.

```json
{
  "answer": "이건 사육자들 사이에서도 의견이 갈리는 부분이야…",
  "source_ids": ["S12", "S15"]
}
```

앱은 `answer`를 대화로 표시하고, `source_ids`로 출처 정보를 조회해 "참고 자료 보기"에 넣는다.

### V0 / 이후

- **V0**: 벡터 DB 없이 지식 자료를 시스템 프롬프트에 `[S12] 내용…` 형식으로 넣는 방식에서도 동작
- **이후 RAG 전환**: 검색된 조각에 출처가 붙어 있어 그대로 이어짐
- 모델 제공사의 출처 표시 기능도 있으나, JSON 방식은 모델과 무관하게 동작해서 V0엔 이쪽이 단순

### 주의점

- **없는 출처를 지어낼 수 있음** → DB에 실제로 있는 ID만 표시, 나머지는 버림
- **"정확한 인용"이 아님** → UI 문구는 "출처"가 아니라 **"참고 자료"**
- **참고 자료가 없는 경우** (`source_ids` 비어 있음) → 박사가 "이건 내가 가진 자료로는 확실하게 말하기 어려워"라고 답함 → "모르면 모른다" 기준 충족

### 진짜 작업량

기술보다 **자료 큐레이션**. 신뢰할 만한 자료 선정 → 조각으로 나누기 → 출처 기록.
V0에서 가장 시간이 많이 드는 작업이 될 가능성이 높음.

## V2 메모: B의 실사용자 역할

- 원하는 것: 집에 없을 때의 안심 (겨울 히터 고장, 여름 폭염·정전)
- Wi-Fi 온습도계 연동 + 위험 시 원격 알림 → **유료 기능 후보**
- BLE는 휴대폰이 근처에 있어야 해서 원격 요구를 못 채움
- 센서 하드웨어 직접 제작 X → 시판 Wi-Fi 온습도계 중 API 제공 제품과 연동

## 도출된 요구사항

| 영역        | 요구사항                                                        |
| ----------- | --------------------------------------------------------------- |
| 온보딩      | 박사의 첫 인사 질문으로 3갈래 분기 (입양 전 / 처음 / 경험 있음) |
| 사용자 정보 | 경험 수준 저장, 설정에서 변경 가능                              |
| 개체 등록   | 숙련자는 선택 항목 펼침 (화면은 동일)                           |
| 박사        | 경험 수준에 따라 설명 깊이 조절                                 |
| 박사 품질   | 정확성·균형·맥락·실행 가능성·정직함 5가지 기준                  |
| 참고 자료   | 답변 아래 "참고 자료 보기" 접힘 표시                            |
| 지식 자료   | 조각마다 ID + 출처 정보 저장                                    |
| 박사 출력   | 답변 + 참고 ID 구조화 출력                                      |
| 검증        | 존재하지 않는 ID 필터링                                         |
| 박사 정직함 | 참고 자료 없으면 확실하지 않다고 답변                           |
